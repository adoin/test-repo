# 复杂合并测试：订单结算升级

这是 Git Agent 的本地测试与截图用例，全部客户、订单与支付结果均为虚构测试数据。
不调用网络、不支付、不读取真实凭据。直接在原来的 `D:\workspace\test-repo` 中测试。

## 两个分支的需求

左侧 `codex/complex-checkout-left`：

- 客户标识做 Unicode NFKC 规范化、去除首尾空白并转为小写；收据隐藏邮箱用户名的一部分。
- 黄金会员享受商品小计 10% 折扣；商品小计达到 80 时免运费；支持 EU 20% 税率。
- 支付前检查风险；幂等键包含客户标识，避免不同客户的订单号碰撞。
- 将旧支付模块迁移到 `payments.mjs`，新接口使用整数分 `amountMinor`，删除旧模块。

右侧 `codex/complex-checkout-right`：

- 客户名称内部的连续空白合并为一个空格，客户键中的空格替换成连字符。
- `WELCOME5` 优惠券减 5，可与会员折扣叠加但折扣不超过商品小计。
- 非免邮订单的新费率为标准 7、加急 15；支持 US 8% 税率。
- 支付前计算税费并检查库存；成功后记录审计信息；收据包含订单号、金额、币种和审计编号。
- 在旧支付模块中增加最多 3 次重试；用 `simulatedFailures` 模拟临时失败，无真实网络操作。

## 合并目标

两边的需求都保留，不应通过删除一边的功能让测试通过。
把右侧的支付重试行为迁移到左侧新模块；保留旧模块已删除的设计，并更新调用者。
处理代码冲突之外，还要检查未产生冲突的新支付模块、审计模块和测试之间是否一致。
结算顺序应为验证、风控、库存、税费、支付、审计、收据，共 7 步。

建议先打开 `order.mjs` 截图，它有多个独立业务冲突；再检查 `pricing.mjs`、`customer.mjs`
及旧支付模块的删除/修改冲突。只有确实运行 AI 分析后才把 AI 建议用于实际界面截图。

## 本地验证

保留未解决状态时，运行测试失败是预期行为。解决并保存所有冲突后，从仓库根目录运行：

```sh
node --test merge-lab/complex-checkout/*.test.mjs
node merge-lab/complex-checkout/acceptance.mjs
```

`acceptance.mjs` 检查两边需求组合后的行为，不包含参考实现，也不会改动文件。
这里只需要 Node.js，不需要安装依赖。不要推送这些测试分支。
